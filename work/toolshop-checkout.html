One purchase, four layers

Project
toolshop-automation
Layers
API, UI, database, mail
Decision record
ADR 0005

The problem

A checkout is the one flow where every layer can lie independently. The page can say the payment worked, the API can answer 201, the invoice row can be missing, and the customer can get no email — in any combination. A suite that only drives the UI will report on the first of those and nothing else.

What I built

One purchase, followed all the way through:

API      an account and a product, created through the application
UI       storefront -> cart -> sign in -> address -> payment
DB       the invoices row, its line, and the total
mail     the confirmation the customer actually received

The setup happens through the application's own API rather than by seeding the database, so the test never depends on a schema it does not own. The assertions then go the other way — down to SQL and to the mailbox — because that is where the evidence is that something was really persisted and really sent.

What it found

On this application, one press of “finish” shows the payment success message and places no order at all.

The cause is in the payment component. checkPayment() fires its request and then returns the state field's value before the response arrives. On the first click that value is undefined, the result === true guard fails, and POST /invoices is never sent. The response then sets the field to true, so a second click works.

Measured: with one click, no POST /invoices appears in the browser network log and no invoice row is written. With two clicks, the request is sent and answers 201.

The user-visible half is what makes it worth its own test. The success message appears on the first click, so the page reports success while nothing was ordered — and the invoice call's error handler is empty, so a genuine failure would look exactly the same. A suite that asserted on the payment message would have reported this as passing.

Why it is quarantined rather than fixed or deleted

The application is third-party here, so I cannot fix it in this repository. That left two options: assert the broken behaviour, which turns a defect into a requirement and means the suite goes red the day it is fixed — or say what should happen and mark it known.

@Quarantine is that mark. It is excluded from the blocking run, kept visible, and run on a schedule so its status stays observable. It is not a retry, and nothing about it is hidden. The rest of the slice — invoice row, invoice line, confirmation email — is still verified by driving the application the way it actually behaves, in exactly one documented place.

The related decision: evidence nobody has to remember

The suite I assessed before this one captured failure evidence through a field each test set by hand at the end of its body, read by an @AfterEach that attached a screenshot when the value was anything else. There were 258 call sites. About fifteen were missing or wrong, so those tests attached a screenshot on every passing run — and the failures that most needed evidence had none.

A convention applied 258 times is a convention that is applied 243 times. The fix is not more discipline, it is removing the call site. So there is one extension, registered by ServiceLoader, applying to every UI test with nothing to remember and nothing to extend. On failure it attaches the screenshot, the Playwright trace, the page URL, the failed requests and the browser console.

Getting that right needed one measurement rather than an assumption: the evidence is not all available at the same moment. A screenshot needs an open page; the trace zip is only written when the browser context closes. So there are two hooks, and which one collects what was verified with a deliberately failing test rather than reasoned about.
