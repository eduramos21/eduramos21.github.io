A selection that runs nothing must fail

Project
toolshop-automation
Layer
Build and execution, on Gradle 9.7.1 and JUnit 6.1.3
Decision record
ADR 0003

The problem

In a large Java suite I assessed before starting this framework, most of the UI tests were reachable only through catch-all suites, so they ran in no smoke job and no regression job. Separately, suite selection there was driven by a CI job-name string, and an unmatched name produced a Gradle command with empty property values rather than an error.

Both are the same failure: a run that executes nothing and reports green. It is the failure mode worth designing against hardest, because unlike a red build it gives no signal at all that something is wrong.

The assumption that was wrong

I planned on Gradle 9's failOnNoDiscoveredTests, which defaults to true. The upgrade guide's wording, “test sources are present, but no test was selected for execution”, reads exactly like it covers this. So I measured it, on a module with one passing test:

ConfigurationResult
includeTags("doesnotexist"), defaultsBUILD SUCCESSFUL
plus failOnNoDiscoveredTests = true explicitlyBUILD SUCCESSFUL
plus filter.isFailOnNoMatchingTests = trueBUILD SUCCESSFUL

Neither property fires. JUnit tag filtering is a post-discovery filter: the test class is discovered, then removed. “No tests discovered” is therefore false. One was discovered and zero were executed, and Gradle's guard only covers the discovery stage. filter.isFailOnNoMatchingTests is a different mechanism entirely; it governs Gradle's own --tests patterns, not JUnit Platform filters.

Both properties stay set anyway, because they cost nothing and they do catch --tests typos, with a comment pointing at the decision record, so nobody re-derives the wrong conclusion from their names.

What I built

Two halves. First, thirteen tags as annotations rather than strings, so @Smoek is a compile error instead of a test that quietly belongs to no suite. Twelve files of four lines each, and it buys the thing that matters.

Second, verifyTestSelection: one task in the root build that finalises every Test task, sums executed tests across every module's JUnit XML, and fails on zero.

Where the guard could live was the whole problem

The instinct is to put it in the conventions plugin with everything else, failing each module that selected nothing. That is wrong, and the reason is structural: there is one layer tag per module, so -Ptags=api is supposed to select zero tests in the UI and data modules. Only zero across the whole invocation is a mistake.

A per-module guard would have produced a false failure on the most ordinary command in the vocabulary, and would have been switched off within a week. The root build is not a compromise here; it is the only place that can see the thing being checked.

Two more details that are decisions rather than mechanics:

  • It is only wired into the task graph when -Ptags is present, so an ordinary run has one fewer task and a configuration failure reports one error instead of two.
  • Its failure message lists the tag vocabulary by reading the annotation file names in the core module, so the build holds no second copy of the list to drift out of date. A test keeps a file name and the tag it declares in step. Without it, that message could go quietly stale, which is the same class of bug one level up.

Reading the JUnit XML is safe against stale results because Gradle wipes a task's output directory when it re-executes, and changing -Ptags changes the task's inputs, so a re-run always rewrites. I checked that rather than assuming it.

The limits, stated

A single-module invocation can still pass wrongly: ./gradlew :core:test -Ptags=x leaves the other modules' test tasks out of the graph, so their result directories keep XML from an earlier run and get counted. The exact guarantee holds for any invocation where the test tasks actually run, which is every form CI and the entry script use. Closing it properly needs per-task participation through a build service, which is more machinery than the case is worth.

And -Ptags=quarantine finding nothing is good news, but the guard fails it, because it cannot tell an empty quarantine list from a typo. The obvious fix is a flag that suppresses the guard, which is a flag that ends up in a CI file silencing a real problem. It stays open until the scheduled job that needs it actually exists.

What it verifies

./gradlew test -Ptags=doesnotexist fails, and ./gradlew test -Ptags='smoke & admin', a valid expression that matches nothing, fails too. That now tests my own guard rather than an assumed Gradle behaviour. Without it the whole tagging scheme is decorative, because a mistyped tag produces the exact silent-green outcome the tagging exists to prevent.
