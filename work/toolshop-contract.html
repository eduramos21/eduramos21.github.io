Contract validation nobody can skip

Project
toolshop-automation
Layer
API, using REST Assured and Java 21
Decision record
ADR 0007

The problem

The suite I wrote this framework against advertised OpenAPI contract validation in its documentation. What actually existed was a private method with no callers, no specification files, and no test that used it.

That is the failure mode worth designing against. Contract validation that is opt-in is contract validation that gets opted out of, because the tests that need it most are the ones nobody remembered to add it to.

What I built

The validator is a REST Assured filter on the shared request specification. Every call any test makes is validated. There is no way to write a test that skips it, and a new test gets it without asking for it.

The document is fetched from the running application at /docs rather than committed into the test repository. A committed copy is a contract the test repository asserts against itself, and it goes stale silently.

What it found

Turning it on failed 28 of 41 tests, from thirteen distinct disagreements. Every one of them was the document under-reporting what the application actually answers:

  • POST /invoices answers 201 where the document lists only 200
  • every administrative route answers an undocumented 403
  • a locked account answers an undocumented 423
  • POST /users/register answers 409 for a duplicate email, documented as 422

So every contract in this layer was taken from probing the running application rather than from reading the specification. The specification being wrong then became something worth asserting in its own right, which is what the validation step is now for.

The part that took the time

The document is OpenAPI 3.2, and no Java validator supports 3.2. The parser does not recognise the version, falls back to Swagger 2 parsing, and then rejects content and requestBody as unexpected on every operation in the file. Setting the version to 3.1.0 left exactly one complaint: seven paths declare a query operation. QUERY is a real HTTP method that OpenAPI 3.2 added, and the application really does use it, since the storefront sends QUERY /products, so this is a genuine 3.2 document, not a mislabelled one.

The document is therefore normalised in two ways and no others: the version is set to 3.1.0, and the query operation is removed from the seven paths that have one. Both are removals of things the suite does not exercise. /products keeps its get, which is the operation the suite calls. A test asserts exactly which operations were dropped, so the cost of the normalising cannot grow unnoticed.

What it cost

Thirteen known deviations, declared individually in a whitelist rather than as a blanket relaxation. A test asserts that each one is still a deviation, so when the application's documentation is finally corrected the build tells me the entry can be removed. A whitelist that only ever grows is a whitelist nobody reads.
