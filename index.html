About

I have spent thirteen years in software quality, the last seven of them remote. Most of that time has gone into the same problem from different angles: how do you get a test suite to tell you something true about the product, on the day you need to know it, without a person having to remember anything.

At the moment that means a Gradle multi-module framework in Java — Playwright for the UI, REST Assured for the API, SQL for what actually got persisted — and a determinism module for generative-AI output that cannot be exact-matched. Before that I led QA through a two-year EMV and PCI PA-DSS certification under external audit, which is where I learned what evidence has to look like when somebody outside your company is going to read it.

I write frameworks so that the wrong thing is hard to do: tags that are annotations instead of strings, so a typo will not compile; contract validation on every call, so no test can opt out; failure evidence attached by the framework, so nobody has to remember a screenshot. The three case studies below are each one of those decisions and what it cost.

Selected work

Three decisions from toolshop-automation, a framework I built against the Toolshop demo application — Java 21, Gradle 9, JUnit 6, Playwright, REST Assured. Each page is one decision, what it found, and what it cost. Every number comes from that repository.

  • Contract validation nobody can skip

    I moved OpenAPI validation onto the shared request specification as a filter, so every call any test makes is validated and no test can opt out. Turning it on failed 28 of 41 tests, from thirteen distinct disagreements between the document and the running application.

    28 / 41 tests failed the first time it ran

  • One purchase, four layers

    A single checkout followed through API, UI, database and mailbox, because each of them can disagree with the others. It caught a defect where one press of “finish” shows a payment success message and creates no order — a suite asserting on that message would have reported it passing.

    0 orders behind a success message

  • A selection that runs nothing must fail

    Thirteen tags as annotations rather than strings, so a misspelled tag will not compile, plus one guard in the root build that fails any run whose tag expression matched zero tests. Where that guard could live turned out to be the whole problem.

    13 tags a typo cannot get into

Two more decisions in that repository that did not get their own page: accessibility is asserted against a per-page baseline rather than against zero, so a new violation and a fixed one both fail the build; and the same bytecode runs against local Docker, CI and the hosted deployment with only configuration changing.
