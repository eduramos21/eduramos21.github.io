About

I have spent 13 years in software quality, the last seven of them remote. Most of that time has gone into the same problem from different angles: how do you get a test suite to tell you something true about the product, on the day you need to know it, without a person having to remember anything.

At the moment, for me and my team that means a Gradle multi-module framework in Java, with Playwright for the UI (recently migrated from Selenium), REST Assured for the API and SQL for what actually got persisted, plus a determinism module for generative-AI output that cannot be exact-matched. Before that I led QA through a two-year EMV and PCI PA-DSS certification under external audit, which is where I learned what evidence has to look like when somebody outside your company is going to read it.

I write frameworks so that the wrong thing is hard to do. Instead of strings I prefer tags as annotations, so a typo will not compile. I bet on contract validation on every call, so no test can opt out and failure evidence attached by the framework, so nobody needs to remember a screenshot. The three case studies below are each one of those decisions and what it cost.

AI determinism-core

Catching when the model quietly starts giving worse answers

A model call can be subtly wrong in a way an ordinary pass or fail test never catches. This suite runs the AI many times against a fixed input and checks every field against a rule, so drift turns up in a nightly run instead of in production.

You cannot exact-match a model

Ask a regression test whether the output equalled X and a model breaks it on day two. The wording shifts, a part id changes, an enum drifts. The right question is not does it equal X but is every field still within what is allowed. And because a model can be inconsistent, you have to ask more than once.

One fixed input, N runs, every field checked

  1. Fixed input Report text A canned description plus the ids it needs.
  2. Run ×N Feature webhook The API test posts the same body N times, no browser involved.
  3. Collect N results Each one a full field set.
  4. Evaluate Rules Each field against the rule bound to it.
  5. Report Tick or cross per rule Actual against allowed.

Every run is checked on its own, so drift on any single run fails the case.

Four kinds of check cover every field

The engine does not know which feature it is testing. Each field is bound to one of these.

  • Allowed set The value must be one of a fixed enum, or of a list exported from the data the feature reads. category in {SCRATCH, DENT, ...}
  • Allowed range A numeric value must fall inside bounds. The engine provides it; no numeric field uses it yet. 0.0 <= x <= 1.0
  • Cross-field A relationship between fields on the same result has to hold. These cost nothing to run and catch the worst failure, which is the model inventing certainty it does not have. empty part_id => follow_up set
  • LLM judge Free text goes to a separate model that returns pass or fail against plain-language criteria. description reads as a real, laconic note

Free text is graded by its own workflow

A description cannot be checked against a list, so it goes to a small judge workflow that QA owns: a webhook in, a model call, a structured verdict out. It sits behind an interface, so no model credential lives in the test code and an offline stub replaces it entirely.

  1. Send { content, criteria } the field text, plus what “good” means for this fixture
  2. Judge the workflow calls the model at temperature 0, pinned, forced to JSON
  3. Verdict { pass, reason } a false is a real finding, and the reason says why
  4. Fail loud a broken judge is a hard test failure, never a fabricated false. An error and a disagreement are different things.

What it caught on the first run

Four fixtures ran. Three passed. One failed, correctly.

Input “Small stone chip on the windshield, happened on the highway.”
Output description: "Small stone chip on windshield; exact side not specified, assumed right side."
Criteria A laconic one-line note naming a stone chip on the windshield, matching the input.
Verdict Fail Added an unsupported “right side” assumption, and a windshield has no side, plus meta-commentary. Not laconic, not faithful.

A true positive. The classifier invented detail and editorialised, against the rules in its own prompt. Nothing in an ordinary test would have flagged it, because the flow worked and the payload was well formed. What the suite caught was the drop in quality.

The engine underneath, meaning the repeat runner, the rules and the reporting, has no knowledge of the feature and no production dependencies at all. The next model-backed feature plugs in its own result type and fixtures rather than a new framework. It runs nightly, never blocks a pull request, and prints actual against allowed on every failure, so the ticket writes itself.
